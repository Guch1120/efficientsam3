# ExecPlan ガイド
このファイルは，`docs/plan.md` を ExecPlan として運用するための補助ルールです．

## 目的
- 複雑な作業を self-contained な計画書として維持すること
- 途中参加の読み手でも，この文書だけで目的と現在地が分かる状態を保つこと
- 実装しながら得た知見を計画へ反映し，次の意思決定を容易にすること

## 基本原則
- `docs/plan.md` は静的な設計書ではなく living document として扱う．
- 実装前の想定と，実装後に判明した事実を同じ文脈で読めるようにする．
- コード変更，実験結果，失敗，方針変更は必要に応じて `docs/plan.md` に反映する．
- `docs/log.md` は時系列の詳細記録，`docs/plan.md` は現在の正規状態と次の打ち手を示す要約として使い分ける．

## 推奨セクション
`docs/plan.md` には少なくとも次の情報を持たせる．

1. Purpose / Big Picture
2. Current Findings
3. Milestones
4. Validation Strategy
5. Progress
6. Surprises & Discoveries
7. Decision Log
8. Risks / Open Questions

必要なら，対象リポジトリに合わせて名称は日本語にしてよいですが，役割は維持してください．

## 記述ルール
- 目的は数値目標と利用シナリオを含めて簡潔に書く．
- 現状は，確認済みの事実と未確認の仮説を分けて書く．
- マイルストーンは順序と完了条件が分かるように書く．
- 検証方法は，何を比較し，どの指標で判断するかを明示する．
- 発見や驚きは，元の想定を覆した事実を優先して残す．
- 判断履歴は，何を採用し，何を見送ったかが追えるようにする．

## 更新タイミング
- 新しい比較実験を完了したとき
- 方針を変更したとき
- 想定外の失敗や制約が見つかったとき
- 次回の開始地点を明確にしたいとき

## 書かなくてよいこと
- 一時的で価値の低い試行錯誤の細部
- すでに `docs/log.md` にだけ残せば十分な逐次ログ
- 読み手の意思決定に影響しないノイズ

## 完了条件
`docs/plan.md` を読めば，少なくとも次が分かる状態を目指す．

- 何を達成したいか
- 何が分かっていて，何が分かっていないか
- いまどこまで進んだか
- 次に何をすべきか
